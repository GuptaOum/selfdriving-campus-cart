Build stages: what to wire, what to test, in what order

Nine stages from a bare bench to an autonomous cart. Each one adds a single subsystem and ends with a gate you must pass before wiring the next. Never add two things at once — when something breaks you need to know which addition caused it.

Power architecture

LiPo ──► ESC ──► BLDC motor └─ BEC 5-6V ──► PCA9685 V+ (servo power only) Power bank 5V/3A ──► Pi 4B USB-C ALL GROUNDS TIED: LiPo/ESC ── PCA9685 ── Pi ── sensors

Two rules that cause most RC-car Pi failures.

Never power the Pi from the ESC's BEC. Motor current spikes brown out the Pi, and you will spend a week chasing "random reboots" that look exactly like software bugs.

Common ground is mandatory. A PWM signal is meaningless without a shared reference. A missing ground shows up as a twitching servo or no response at all.

Any time you add a load, re-check vcgencmd get_throttled. It must print 0x0; anything else is undervoltage or thermal throttling.

STAGE 0

Bench prep, nothing moves yet

Get a Pi that boots reliably with enough free RAM to run the models later. On 2 GB this stage is not optional housekeeping — it is what makes the rest fit.

Electronics

  • Heatsink on the Pi at minimum; a small fan (₹200) is worth it — sustained inference thermally throttles a bare Pi 4.
  • Flash Raspberry Pi OS Lite 64-bit, headless. The desktop costs ~400 MB of your 2 GB and you have none to spare. Enable SSH in Imager.
  • Power bank → Pi. Confirm it delivers a genuine 5 V/3 A, not 2.1–2.4 A.

Software

sudo apt update && sudo apt install -y pigpio python3-venv i2c-tools zram-tools
sudo systemctl enable --now pigpiod
sudo raspi-config   # enable I2C, enable serial PORT, disable serial CONSOLE
Use zram, never SD-card swap. Swapping to the SD card will destroy it in weeks and the failure looks like random corruption.

Gate 0

  • vcgencmd get_throttled returns 0x0
  • free -m shows at least 1.6 GB free
STAGE 1

Drivetrain and RC override

You mostly have this already. It still gets its own gate, because the RC transmitter is your emergency stop for every stage that follows — the manual path must be bulletproof before any autonomy exists.

Free the UART for iBUS in /boot/firmware/config.txt:

enable_uart=1
dtoverlay=disable-bt

Then sudo systemctl disable hciuart and delete console=serial0,115200 from cmdline.txt — the serial console will eat your iBUS bytes otherwise.

Software

i2cdetect -y 1                          # must show 40
donkey calibrate --channel 1 --bus 1    # steering: left/right pulse values
donkey calibrate --channel 0 --bus 1    # throttle: stop/forward/reverse
Put the measured numbers into PWM_STEERING_THROTTLE in myconfig.py. The values sitting in config.py are placeholders and will not drive your hardware correctly.

Gate 1 — wheels off the ground first, then on

  • python manage.py drive — sticks move servo and motor correctly
  • CH5 switch changes mode between user, local_angle, local in the log
  • Five minutes of manual driving: no reboots, no twitching
STAGE 2

Camera and the offline vision go/no-go

The cheapest stage to fail, so it comes before everything else. You are deciding here whether the pretrained model actually sees your campus — and whether a 2 GB Pi 4 can run it at all.

Electronics

  • USB webcam into the Pi's USB 3.0 (blue) port
  • Set CAMERA_TYPE = "CVCAM" — the WEBCAM option uses pygame and is flaky on Linux

On your laptop, in a venv

python -m venv .venv && .venv/Scripts/activate
pip install transformers torch onnx onnxruntime ultralytics
python scripts/export_models.py

Copy exported_models/ into mycar/models/ on the Pi.

Collect footage

Walk every planned route holding the webcam at the car's real camera height and angle. The clips must include sandy or unpaved stretches, at least one speed breaker, people walking, and a junction where the path forks.

python scripts/vision_bench.py --video campus_walk.mp4 \
  --seg-model models/exported_models/segformer_sidewalk_int8.onnx \
  --seg-labels models/exported_models/segformer_labels.json \
  --yolo-model models/exported_models/yolov8n_ncnn_model --out annotated.mp4

Gate 2 — watch annotated.mp4, read the printed numbers

  • Green mask covers the ground you would actually drive on, including sand. If not → fine-tune with ~100 labeled campus images on free Colab, re-export, re-run.
  • Segmentation ≥ 1 FPS and peak RSS under ~1200 MB. If not → Pi 5 8 GB; no code changes needed.
  • Steering value swings the correct direction as the path curves

Do not proceed until this passes. Everything downstream assumes the mask is trustworthy.

STAGE 3

Segmentation pilot on the car, wheels off the ground

First time the model commands the servo. No new wiring — the risk here is entirely in calibration.

Camera calibration — do it once, properly

Mount the camera rigidly at a fixed height and tilt. If it moves later, your corridor calibration is void and the car will misjudge whether it fits through gaps.

  1. Tape a 1 m × 1 m grid on the ground in front of the car.
  2. Capture a frame; measure how many pixels wide your (car width + 20 cm margin) corridor spans at the bottom of the image.
  3. Set SEG_CORRIDOR_FRAC = that_width_px / image_width_px.
USE_CAMPUS_AUTONOMY = True     # everything else still False
CAMERA_TYPE = "CVCAM"

Gate 3 — car up on a box, wheels spinning free

  • Camera pointed at a clear path → wheels straight, motor spins slowly
  • Block the lens with cardboard → throttle goes to zero
  • Angle the camera so the path sits off to one side → steering follows it
  • Flip CH5 to user mid-run → RC takes over instantly
STAGE 4

Ultrasonic safety layer

Three HC-SR04s giving you a hard stop that does not depend on the camera or the model. This is the stage where wrong wiring destroys hardware.

HC-SR04 ECHO outputs 5 V. Pi GPIO tolerates 3.3 V. Connecting them directly kills the pin and possibly the Pi. You need one voltage divider per sensor — three in total.

ECHO ──[ 1 kΩ ]──┬── Pi GPIO (6 / 26 / 21) │ [ 2 kΩ ] │ GND

5 V × 2k/(1k+2k) = 3.33 V. Use 1 kΩ + 1.8 kΩ (→ 3.21 V) if you want more margin. TRIG needs no divider — the Pi drives it at 3.3 V, which the HC-SR04 accepts.

Cleaner alternative: buy HC-SR04P (~₹80 each) and power them at 3.3 V. ECHO then swings to 3.3 V and no dividers are needed at all. Range drops to roughly 2–3 m, which is far more than the 80 cm this design uses.

Mounting — this is the speed-breaker fix, don't skip it

  • All three mounted ≥ 10–12 cm above the ground, aimed level or slightly up, so a 5–6 cm breaker passes below the beam. Mounted low, the cart hard-stops at every breaker forever and looks broken.
  • Left and right splayed ~30° outward so they don't hear each other's pings
  • VCC of all three to the 5 V rail (Pi pin 2 or 4 is fine — roughly 15 mA each)

Software

HAVE_ULTRASONIC = True
ULTRASONIC_PINS = {"left": (5, 6), "center": (19, 26), "right": (20, 21)}

Test the sensors standalone before touching manage.py:

cd mycar && python -m parts.ultrasonic

Gate 4

  • Standalone test prints sane centimetre values; a waved hand drops them
  • Full drive, wheels off ground: hand closer than 30 cm → throttle cuts
  • Remove hand → resumes after the five-reading clear streak
  • Walk a speed breaker under the sensors → no false stop
STAGE 5

First real autonomous drive

Wheels on the ground, model in control, you walking beside it with your thumb on the mode switch.

Software

Enable HAVE_YOLO_GUARD = True and start slower than the defaults:

SEG_THROTTLE_CRUISE = 0.20   # slower than default while tuning
SEG_THROTTLE_CREEP  = 0.14

Procedure — a straight, empty, obstacle-free path

  1. Walk beside the car with the transmitter in your hand, thumb on CH5.
  2. Flip to local. Let it drive 10 m. Flip back to user.
  3. Tune: weaving → lower SEG_KP. Cutting corners → raise it. Oscillation that grows instead of settling → raise SEG_KD.
  4. Only once straights are stable, try a gentle curve.

Gate 5

  • 50 m of continuous autonomous driving with no intervention
  • Deliberately step in front of it — it stops
STAGE 6

Speed breakers and rough surfaces

Teach it to cross the yellow-and-black plastic breakers instead of stopping dead at them — and confirm the chassis can physically clear one.

Physical gate — measure before you drive at one

  • Wheel diameter ≥ roughly 2× breaker height (110–130 mm wheel for a 55–65 mm breaker)
  • Belly clearance at full suspension compression clears the crest with ~20 mm to spare
If either measurement fails, mark that route impassable in the campus graph and route around it. Do not try to power over it — you will beach the chassis or strip the 20-tooth pinion.

Software

HAVE_BREAKER_DETECT = True is on by default. Verify it on your recorded footage first: vision_bench.py prints [BREAKER] on the annotated frames where it fires.

Optional MPU6050 (₹150) catches unpainted humps, which have no stripes to detect. Wire it to the same I²C bus as the PCA9685 — address 0x68, no conflict with 0x40 — and trigger creep from the pitch jolt.

Gate 6

  • Cart approaches a striped breaker → drops to creep, crosses perpendicular, resumes
  • It does not stop dead on top of it
STAGE 7

GPS, geofence, junctions

Give it a map. GPS never steers — it answers "which junction is next" (a 10 m question) and "am I still inside the allowed area", both of which 2–5 m accuracy can handle.

Electronics

  • NEO-M8N with an active antenna, clear sky view, mounted away from the ESC and the Pi — both are RF-noisy. A small ground plane under the antenna helps.
  • NEO-M8N → USB-TTL adapter → Pi USB port. Not the UART pins: iBUS owns /dev/serial0, and moving it risks breaking your working RC link.
  • GPS TX → adapter RX, GPS RX → adapter TX, VCC/GND per the module's spec

Software

sudo apt install -y gpsd gpsd-clients
sudo dpkg-reconfigure gpsd     # device: /dev/ttyUSB0
cgps -s                        # confirm a 3D fix before anything else

On the laptop, build the campus graph and copy it to mycar/:

python scripts/build_campus_graph.py --point <lat>,<lon> --dist 800
HAVE_GPS_NAV = True
GEOFENCE = [(lat1, lon1), (lat2, lon2), ...]   # WIDE margin — GPS error is 2-5 m
MISSION_REQUIRES_GPS = True                     # outdoor only; False indoors
Survey the routes first. Walk each one with cgps open. Tree cover and building canyons produce 10 m+ error or no fix at all. A route with dead zones needs either a different path or buffered positions replayed on reconnect.

Gate 7

  • Carry the powered car (motor disconnected) outside the geofence → log shows GPS UNSAFE — fail closed
  • Drive a route with one junction; the log prints LEFT/RIGHT at the right place
  • The cart takes the correct branch at the fork
STAGE 8

App, teleop, delivery

The part the user sees: drop a pin, watch the cart come.

FastAPI + SQLite + WebSocket backend, React + Leaflet PWA on the front, Tailscale to reach the Pi behind campus NAT without asking IT for port forwarding, and MediaMTX/WebRTC for the operator video feed.

Add the deadman heartbeat before any remote driving: a command every 200 ms, throttle cut after 500 ms of silence. Without it a Wi-Fi dropout means the cart keeps driving at its last commanded throttle.

The second camera (USB 720p for the operator, PiCam for the model) belongs here — but check RAM headroom first. On 2 GB this is the single most likely trigger for an out-of-memory kill.
